This makes the HANDOFF row Q1 question (`(v_b − v_i)Δλ`: free-slip or no-slip?) concrete — **user decision, still open**; WORK-005/006 keep free slip.

## 4. Findings the next work document must assume
* **The exact path is currently SLOWER.** Measured (`docs/work/refs/review5_speed_probe.py`, 100 + 100 steps): dam break nx67 **43.4 → 78.9 ms/step** (+82 %), sloshing nx200 **69.7 → 113.8 ms/step** (+63 %) with all four switches on — and `_solid_samples` (16 ms / 35 ms, from `deltasph-profile.md`) is still being built in both runs, because `near` is taken from it. Deleting it alone gives ≈ 62 / 79 ms: still slower than today.
* **Where the 36 ms go** (`review5_cost_probe.py`, developed dam-break state, 468 near particles, 4 edges; the sum 36.1 ms matches the measured +35.5): `tensile_vector_scene` 10.9 ms × 1 call/step; `lap_lambda_scene` 6.65 ms × 2 = 13.3 (two adjacency builds per call); `cover_vector_scene` 3.06 × 3 = 9.2 (one build per call); `cone_area_scene` 0.5 × 6 = 2.8 (no adjacency).
* **The adjacency is kernel-dependent and holds the pair channels** (the *why*, with measurements, is in `docs/scene-architecture.md` §6b and `refs/review5_adjacency_why_probe.py`: it stores the integrals `lam, g0, m1, g1` of its own kernel per pair, `sceneOperation` ignores the kernel of its `props` when an adjacency is passed — `lw2` with a `cone` adjacency returns the `cone` result bit-for-bit — and nothing checks `SceneAdjacency.kernel`; WORK-006 T6.2 adds the guard). `buildAdjacency` for a `SurfaceRep` evaluates the edge channels of the *kernel* (a `cone` adjacency used by `lw2` / `w2p5` gives results off by 0.18 / 0.34 against scales 0.53 / 0.28); the operation afterwards is ~0.02–0.2 ms. So the cost is the channel evaluation at build time: all-N build for `cone` 2.7, `lw2` 3.4, `Wendland2` 4.0, **`w2p5` 10.8 ms**. Sharing works only **within one kernel**: `cover_vector_scene` with one adjacency is bit-identical (0 difference) and 2.93 → 0.18 ms; `lap_lambda_scene` builds two adjacencies of `lw*` (Density, Covariance) for no reason — one shared adjacency is bit-identical (0 difference) and 7.17 → 3.65 ms (C2), 9.82 → 4.78 ms (C4) per call (`review5_lap_adjacency_probe.py`).
* **Chebyshev vs monomial, same state** (`review5_cheb_resolution_probe.py`, `tensile._register` pinned): `w2p5` monomial 24.8 ms / `(16,8)` 10.9 / `(8,6)` 6.7 / `(6,4)` 5.4; `w4p5` monomial 51.8 / `(16,8)` 13.7 / `(8,6)` 8.6 / `(6,4)` 6.5; error against `(16,8)` (relative to `max|T|`): `(12,6)` 1e-15, `(8,6)` 1.9e-11 (C2) / 7.6e-11 (C4), `(6,4)` 1.1e-8 / 1.7e-8; monomial 1.0e-7 (C2) / **3.7e-3 (C4)**. The Chebyshev plan is already 2.3–3.8× faster than the monomial one here; `(8,6)` would save a further 4–5 ms/step at 1e-10 (the polar quadrature it replaces has 1.4e-2). Not taken in WORK-006 (vertex-proximity accuracy of `(8,6)` is only known to degrade within 0.01 H of a vertex; it is a phase-2 knob). Gotcha: `tensile._register` **resets** `warpbc.STABLE_KERNELS[name]` to `(16, 8)` on every call.
* **The solver code that WORK-006 touches** (`deltasph2d.py`): `near` (`lam.sum(0) > 1e-9`) exists in `rhs` and `_surface_state` and is the *only* thing the exact paths take from `_solid_samples` (`samples = (near, self._solid_samples(x, near))`); the exact branches of `_detect_surface` / `shift` / `rhs` do not use `ins, u, rk, dr, dphi`. Consumers outside the solver: `deltasph_detcmp.py` (polar-vs-exact detector comparison, meaningless once polar is gone), `deltasph_profile.py` (tracks `_solid_samples`), tests `test_deltasph_cover.py`, `_cone.py`, `_tensile.py`, `_tensile_c4.py`, `_viscosity.py` (use `_solid_samples` / the polar value as the *independent reference* of the exact-vs-quadrature accuracy checks), and `test_deltasph.py::test_wall_viscous_term_matches_the_half_plane_integral` (pins the **pairwise** wall term: it fails the moment the pairwise term is removed).
